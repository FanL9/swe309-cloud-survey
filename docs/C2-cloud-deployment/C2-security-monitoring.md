# Security, Monitoring and Reliability

## 1. Introduction

This document separates what was actually deployed and verified on the PythonAnywhere free tier on 2026-11-23 from what remains a design proposal for the Cloud Run architecture in B2. Section 7 is the authoritative status table; anything not listed there as implemented is design only.

The deployment under test is the C1 Flask questionnaire application, running at `https://changxuzhu.pythonanywhere.com` on a Beginner (free) account. All data used during testing is synthetic.

## 2. HTTPS and Data Protection

### 2.1 HTTPS Communication

HTTPS is enforced on the live deployment.

- `http://changxuzhu.pythonanywhere.com/` returns `302` with `Location: https://changxuzhu.pythonanywhere.com/`.
- TLS is terminated by PythonAnywhere, which supplies the certificate for the `pythonanywhere.com` subdomain; no certificate was installed by the team.
- Session cookies are issued with `Secure`, `HttpOnly`, `SameSite=Lax` and `Path=/`.
- The survey form is therefore only reachable over HTTPS in normal use.

Evidence: E07.

### 2.2 Data Protection

What is in place:

- Responses are stored in SQLite at `app/instance/survey.db` on the account disk, not in `/tmp`.
- The file is readable only by the account owner (`-rw-r--r--`, owner `CHANGXUZHU`).
- Configuration values, including the secret key and the password hash, are read from environment variables set in the WSGI file and are not present in the repository.
- Logs record request metadata and staff actions but not comment text or client IP addresses.

What is not in place:

- No encryption at rest. Anyone with account or disk access can read the database.
- No backup. There is no copy of the database outside the account.
- No retention policy: responses are kept until the account or database is deleted.

Evidence: E05, E08, E10.

## 3. Access Control and Permissions

Implemented and verified:

- Staff pages require a login: `/staff/`, `/staff/responses`, `/staff/lookup` and `/staff/export.csv` return `302` to `/staff/login` when no session exists.
- Credentials are a username plus a scrypt password hash generated by `python hash_password.py`; the plaintext password is never stored on the server.
- Every staff action that reads or exports responses is logged with the staff username, giving an audit trail.
- Platform-level password protection was found enabled on the web app and was disabled, because it returned `401 Authorization Required` for every request and would also have blocked survey respondents.
- Only the account owner can edit files, restart the web app or read the database. The free plan does not expose per-file roles.

Design only (Cloud Run architecture):

- A dedicated service account for the application, separate from deployment credentials.
- Secret Manager for the application secret and database password.
- An IAM review cycle for human access to the console.

Evidence: E02, E06, E08.

## 4. Monitoring and Logging

### 4.1 Application Logging

Each request produces one line containing method, path, status code and duration in milliseconds. In addition, the application logs:

- application startup, including the environment, storage backend, database path and the number of responses read at startup;
- accepted submissions, with the response identifier;
- rejected submissions, with the reason (`invalid_rating`, oversized body);
- staff login success and failure, with the username;
- staff views and CSV exports, with the username and row count.

Log destination is `app/logs/app.log` on the account disk, plus stdout captured in the platform error log.

Comment text and client IP addresses are not logged. A sample excerpt is stored as E08.

### 4.2 System Monitoring

| Metric | Availability on the free tier |
|---|---|
| Request status and latency | Available in `app.log` (per-request duration) |
| Application availability | `GET /health` returns JSON; no external poller configured |
| CPU usage | Daily total only ("CPU seconds used today"); no per-request view |
| Memory usage | Not exposed |
| Request rate over time | Not exposed; the Web page reports traffic as "tbc" |
| Error rate | Derivable from the log, but no automated alerting |
| Database availability | Only implicit: failures appear as 5xx in the log |

No alerts are configured. An outage is currently noticed by a user, not by the team.

Evidence: E08, E09.

## 5. Peak Traffic Handling

Design calculation (not measured; see E12):

- Peak arrival rate 50 req/s for 600 s gives 30,000 requests.
- At 0.5 s per request, required concurrency is 25.
- The B2 Cloud Run design provides 4 instances x 20 concurrency = 80, which absorbs the peak with headroom.
- Database connections: 5 per instance x 4 = 20, within the Cloud SQL connection limit.

Applied on the live deployment:

- Request validation rejects invalid submissions before they touch the database (verified: HTTP 400 on an invalid rating).
- The request body is capped at 16 KiB.
- The free tier provides one worker and 100 CPU seconds per day, so it cannot serve a 30,000-request peak. This deployment is a verification environment, not a production platform.

Evidence: E04, E12.

## 6. Backup and Recovery

- Persistence is in place: the SQLite file survives a web-app reload. After the reload the startup log reports `responses=6` and the row count is unchanged.
- No backup exists. There is no copy of `survey.db` outside the account and no scheduled export.
- No restoration procedure has been written or tested.
- Recovery currently depends on the account still existing; the free account expires one month after signup.

Evidence: E05.

## 9. Gaps and Improvements

| Gap | Risk | Improvement |
|---|---|---|
| Login lock is in-process only | A reload or a second worker resets the counter | Move the counter to the database or a shared store |
| No backup | Account expiry or disk corruption loses all responses | Nightly `sqlite3 .backup` to external storage, plus a restore test |
| No alerting | Outages are found by users, not by the team | Uptime check on `/health` with email alert; error-rate threshold on the log |
| No log rotation | Disk quota exhaustion stops the app | Size-capped rotation in the logging setup |
| SQLite only | Cannot scale past one writer or survive instance loss | Implement the reserved `STORAGE_BACKEND` path against a managed database |
| No encryption at rest | Disk-level exposure reveals responses | Database-level encryption or a managed service with encryption at rest |
| Free tier expiry | Public URL stops working after one month | Move to the Cloud Run production design before the deadline |
